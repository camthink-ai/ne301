# NE301 抓拍上传服务配置说明（v4.3.1）

> 依据当前固件代码整理（`Custom/Services/Upload/upload_coordinator.c`、`Custom/Core/System/json_config_mgr.c`）。
> 面向设备使用与运维人员，说明各配置项的作用、行为边界、以及可能出现异常的场景与自愈方式。

---

## 1. 概述

抓拍上传服务负责把每次抓拍（JPEG 图像 + 可选推理图 + AI 结果）落盘并按配置的模式上传。

记录统一存放在所选存储卷的 `/captures/` 目录树下，按日期/小时分层：

```
/captures/
  ├── meta/<日期>/<小时>/cap_*.json   # 记录元数据（状态字段在此文件内，落盘后永不移动）
  ├── data/<日期>/<小时>/cap_*_{p,i,a} # 图像数据：p=主图 i=推理图 a=AI结果
  └── index/<日期>.idx                # 当日清单（追加式索引，含墓碑条目）
```

**pending / sent / failed / local 是元数据里的状态字段，不是四个目录**——状态迁移只改写 meta json 里的 `state` 字段并在 index 里追加一条，文件本身不移动。

每条记录有唯一 ID（`cap_<时间戳>_<序号>`），状态迁移为：

```
pending ──上传成功──> sent ──(超过保留时间)──> 删除
   │
   └─重试耗毕/不允许重试──> failed ──(Web 手动重试)──> pending
```

---

## 2. 配置项总览

| 配置项 | 取值范围 | 默认值 | 作用 |
|---|---|---|---|
| 上传模式 mode | 即拍即传 / 批量 / 定时 / 仅本地 | 即拍即传 | 决定抓拍后何时上传（详见 §3） |
| 存储位置 storage | 自动 / 内部 Flash / SD 卡 / 不存储 | 自动 | 记录落到哪个卷（详见 §4） |
| 存储策略 policy | 循环覆盖 / 存满即停 | 循环覆盖 | 满了之后删旧还是拒绝新抓拍（详见 §4.3） |
| Flash 记录上限 flash_max_records | 16 ~ 256 | 32 | 内部 Flash 卷上所有状态的记录总数上限，超限删最旧（仅对 Flash 生效，SD 卡无条数上限） |
| 上传协议 upload_protocol | MQTT / WebHook | MQTT | 上传使用的通道 |
| 批量阈值 batch_count | 2 ~ 20 | 10 | 批量模式下 pending 数量达到该值触发一次上传 |
| 定时节点 schedule | 最多 8 个；Web 界面仅提供半小时粒度（xx:00 / xx:30），API 可设任意分钟（0~1439，非法值归零） | 无 | 定时模式下每天在这些时刻触发上传 |
| 保留时间 keep_sent_hours | 0 ~ 72000 小时 | 72000（永久） | 已上传（sent）记录的保留时长；72000=永久保留，0=上传成功后立即删除 |
| 自动重试 retry_enable | 开 / 关 | 开 | 关闭后首次失败直接进 failed，不做自动重试 |
| 重试次数 retry_max_attempts | ≥0，0 = 不限次数 | 5 | 单条记录的自动重试上限 |
| 上传网络 upload_comm_type | 跟随系统 / 指定某网络 | 跟随系统 | **仅低功耗唤醒抓拍生效**：唤醒时优先拉起指定网络；运行期抓拍始终走系统当前网络 |

> 说明：`max_pending_records` 字段虽在配置与 API 中存在，但当前固件未参与任何限流逻辑，本文不展开。

## 3. 上传模式详解

### 3.1 即拍即传（INSTANT）

- 抓拍后在入队调用内**同步完成上传**才返回；返回成功即"已发出或已进入重试队列"。
- **不依赖本地存储**：即使存储失败（卷满 / 无卡 / 持久化出错），也会直接从内存上传，图像不丢。
- 上传失败时记录留在 `pending/`，等待后续重试；存储为"不存储"时失败即终态。
- **唤醒耗电最高**：每次抓拍唤醒都需要网络在线，是四种模式中唯一"必然拉网"的。

### 3.2 批量上传（BATCH）

- 抓拍后只落盘、立即休眠，**不拉网络**——这是低功耗场景下最省电的模式。
- 触发上传的条件：pending 数量（不含 failed）达到 `batch_count` 阈值，到达阈值的那次唤醒才拉网集中上传。
- 达到阈值的判定发生在**新增抓拍之后**（pending+1 ≥ batch_count），因此实际单批最多可能包含 batch_count + 1 条（上一批遗留 + 本条）。
- 若网络长期不可用，pending 会持续积压，每次唤醒只做落盘。

### 3.3 定时上传（SCHEDULED）

- 抓拍后只落盘；每天在配置的定时节点（最多 8 个）唤醒并集中上传**全部** pending 记录。
- 定时节点以"一天内分钟数"表示（0 = 00:00，1439 = 23:59），非法值归零。
- **Web 界面的选择粒度是半小时**（只能选 xx:00 或 xx:30，新节点默认 08:00）；直接调 API 可设置任意分钟。
- **频率上限 = 每天 8 次**：节点数封顶 8，因此"每小时上传一次"这类高频诉求在定时模式下无法实现，应改用批量模式按阈值触发。
- 未配置任何节点时，该模式实际上不会自动上传（只能靠 Web 手动触发/重试）。
- 与批量模式不同：定时上传**每次到点都全量清空** pending，与积压数量无关。

### 3.4 仅本地（LOCAL_ONLY）

- 只落盘到 `local/`，永不上传、永不参与 flush。
- 唤醒时不需要网络；记录只能通过 Web 查看/下载/删除。

### 3.5 唤醒拉网规则（needs_network）

低功耗唤醒时，系统在服务启动前先判断"这次唤醒是否需要网络"，避免无意义的数秒级网络拉起：

| 模式 | 是否拉网 |
|---|---|
| LOCAL_ONLY | 从不 |
| INSTANT | 每次 |
| BATCH | 仅当本条抓拍达到批量阈值，或存在值得重试的 failed 积压 |
| SCHEDULED | 仅当定时上传节点到期，或存在 pending/failed 积压 |

> `failed` 记录**不参与**批量阈值判定——一批 failed 不会把批量模式从休眠中唤醒，只有 Web 手动重试或（定时模式下）到点才会处理它们。

**开机补传**：上表只约束低功耗唤醒路径。正常运行开机时网络服务照常启动，上传服务启动后会**无条件触发一次清仓**——等待通道就绪（最长 30 秒）后把全部 pending 上传，与当前模式无关（仅本地模式因无 pending 自然空跑）。因此模式切换遗留的待传记录、之前断网期间的积压，都会在下次开机联网后自动补传。若开机时 broker 在 30 秒内未连上，该次补传跳过，等下一个上传触发点。

## 4. 存储位置与策略

### 4.1 存储位置选择

| 位置 | 说明 |
|---|---|
| 自动（AUTO，默认） | 开机时按 SD 卡在位状态选择：有卡用 SD，无卡用 Flash。运行期支持热插拔跟踪：插卡后在下次记录操作时升级到 SD；拔卡后降级回 Flash |
| 内部 Flash | 固定使用片上 littlefs 卷。容量小，受 `flash_max_records` 条数上限约束 |
| SD 卡 | 固定使用 SD 卷。无条数上限，只受卡容量约束。无卡时抓拍按存储失败处理 |
| 不存储（NONE） | 记录不落盘。即拍即传模式下等于"只上传不存档"；其他模式下抓拍直接失败 |

**自动模式的边界**：

- 选择基于**卡在位检测**（非阻塞），不等待挂载完成；实际落盘前对 SD 有最长 3 秒的就绪等待（5ms 步进轮询），超时按存储失败处理——**不会静默改写到 Flash**，避免同一批记录散落两个卷。
- 每次唤醒重新解析：白天运行期插拔、跨休眠周期换卡，最迟在下次唤醒后生效；换卡瞬间的单次状态不一致会在下一周期自愈。
- 记录计数、索引与卷绑定：切换卷后各卷的记录互相独立，Web 列表显示的是当前活跃卷的内容。

### 4.2 Flash 条数上限

- `flash_max_records`（16~256，默认 32）限制 Flash 卷上**所有状态**（pending+sent+failed+local）的记录总数。
- 超限时按循环覆盖策略删最旧记录腾位。
- **边界**：条数上限只在"卷内还有空间"时武装。若剩余空间先耗尽，则由**空间型清理**接管（同样删最旧），实际条数可能低于上限。SD 卡不受此配置影响。

### 4.3 存储策略（满了之后怎么办）

| 策略 | 行为 |
|---|---|
| 循环覆盖（WRAP，默认） | 满了自动删除最旧记录腾出空间，新抓拍照常写入。删除顺序：**sent → local → failed → pending**（先删已上传的，最后才动未上传的），同类内最旧优先 |
| 存满即停（STOP） | 满了不删旧记录，直接拒绝新抓拍 |

**存满即停 + 各模式的行为**：

- 即拍即传：**不受影响**——存储被拒后仍会直接从内存上传（不落盘）。
- 批量 / 定时 / 仅本地：抓拍直接失败（返回无空间错误）。
- **自愈机制**：被拒绝时会顺带做一次"超龄已上传记录"的清理扫描——若保留时间未设为永久，超龄 sent 记录会被清掉，腾出的空间/条数让**下一次**抓拍恢复成功（边界处最多丢一条）。若保留时间设为 72000（永久），则不清理，表现为持续拒绝，直到人工删除或改配置。

### 4.4 保留时间（keep_sent_hours）与清理时机

- 只作用于 **sent**（已上传）记录；pending/failed/local 不按时间删除。
- `72000`（默认）= 永久保留；`0` = 上传成功后立即删除（等于"只传不存档"）。
- **调小保留时间会立即清理存量超龄记录**（在下次清理时机触发时），包括**新插入的 SD 卡**上的历史记录同样按当前配置清理——换卡不会豁免。
- 清理发生在上传通道就绪时的 flush 流程内（含"无 pending 待传"的空转路径）；**通道未就绪（网络不通/服务未启用）时不会执行清理**。因此永久保留 + 不联网的设备，sent 记录不会被清理，属预期行为。
- 清理单轮有时间预算上限（15 秒），超大积压会分多轮完成。

## 5. 重试与失败处理

- 自动重试开关**关闭**时：首次失败直接进 `failed`，只能通过 Web 手动重试。
- 开启时：单条重试次数达到 `retry_max_attempts`（0 = 不限）后进 `failed`。
- `failed` 是**终态**：不会自动回到 pending，也不会被保留时间清理，只占用空间。恢复途径只有 Web 手动重试（单条或全部）。
- 源图像文件丢失/损坏的记录会被直接标记 failed（不消耗重试次数），避免永久卡在 pending。
- 元数据丢失（如断电残留的半条记录）会被索引自愈为墓碑并跳过，不阻塞上传循环。

## 6. 上传协议

| 协议 | 通道就绪判定 | 说明 |
|---|---|---|
| MQTT | 服务运行中 **且** broker 已连接 | 大批量 flush 使用滑动窗口并发（窗口 = batch_count，上限 16），失败记录重试 |
| WebHook | WebHook 服务已启用 | 逐条 POST，行为与 MQTT 模式一致（成功进 sent，失败按重试规则处理） |

通道未就绪时（网络断、服务未启、broker 未连），flush 流程整体跳过——不会空转烧 IO 与电量，pending 保持积压等待下次触发。

---

## 7. 边界与限制（重要）

1. **flush 单轮时间预算**：按积压量动态计算（每条约 3 秒 + 基础 3 秒），**上限 30 秒**。超预算的积压在下一轮继续（定时模式等下个节点，批量模式等下次阈值/手动触发）。
2. **休眠切断与重复上传**：滑动窗口内在途的记录（≤ 窗口上限 16 条）若遇休眠切断，下次会重新发布——接收端可能收到**少量重复**消息，需按记录 ID 去重。这是用有限重复风险换取唤醒时长可控的取舍。
3. **`upload_network`（上传网络）的作用域**：只影响**低功耗唤醒抓拍**时优先拉起的网络；运行期（设备已开机工作）的抓拍始终走系统当前网络。若指定了某个未配置过的网络，唤醒抓拍将无法上传。
4. **时间同步依赖**：定时节点、保留时间清理均依赖系统时钟正确。设备时钟未校准前（首次开机无 SNTP/U0 授时），定时上传不触发、按时间删除的判定不可靠。
5. **SD 卡慢挂载**：落盘前最长等待 3 秒；超时的抓拍按存储失败路径处理（见 §4.3），不会无限阻塞唤醒。
6. **failed 积压不唤醒网络**（批量模式）：设计上避免一堆积压尸体反复把设备从休眠中拉起来；代价是批量模式下 failed 记录需人工在 Web 处理。
7. **即拍即传的失败终态**：存储为"不存储"+上传失败时，该条记录彻底丢弃（无处落盘重试）。

## 8. 常见异常与自愈

| 现象 | 原因 | 自愈/处理 |
|---|---|---|
| 批量模式 pending 一直涨、不上传 | 网络不可达 / broker 未连接 / MQTT 服务未启 | 通道恢复后下次阈值触发或重启开机时集中上传；期间记录不丢 |
| 存满即停后批量/定时抓拍失败 | 卷满或 Flash 条数达上限 | 若保留时间非永久：自动清超龄 sent，下一次抓拍恢复；否则需人工删除或调大保留时间外的清理 |
| sent 记录比预期少 | 保留时间为 0（上传即删）或已超龄被清理 | 属配置预期；改回 72000 可永久保留 |
| 新换 SD 卡后旧记录"消失" | 自动模式卷切换，Web 只显示当前活跃卷 | 原卷数据仍在，切回对应存储位置即可见；注意新卡会按当前保留时间清理 |
| 记录一直 failed | 重试耗尽、源图损坏、payload 超限等 | Web 端单条/全部重试；无法恢复的可直接删除 |
| 接收端偶发重复消息 | 休眠切断在途窗口的重新发布 | 按记录 ID 去重 |
| 定时不触发 | 未配置节点 / 时钟未校准 / 模式未设为定时 | 检查配置；等授时完成后按节点生效 |
| 唤醒后首条抓拍偶发丢失 | SD 慢挂载超过 3 秒等待（存满即停+满卷时边界丢一条） | 属有界损失；即拍即传模式不受影响（内存直传） |

## 9. 手工删改 /captures/ 目录会发生什么

内部 Flash 卷无法从外部访问，实际场景是**SD 卡拔出后在电脑上操作**。索引（index）是记录枚举的唯一依据，文件被外部增删后，设备按下面的规则自愈：

| 用户操作 | 设备行为 |
|---|---|
| 删除 data/ 下的图像文件（meta 还在） | 该记录上传时判定"源图丢失"，**直接进 failed**（不消耗重试次数，因重试也无意义）；Web 列表可见，可手动删除。占计不占空间 |
| 删除 meta/ 下的 .json（数据文件还在） | 索引条目变失效：下次 flush 时被**墓碑排除**（计数/列表不再显示）；残留的数据文件由孤儿清扫逐步回收空间。**完全自愈** |
| 删除 index/ 下的 .idx（或损坏） | 下次开机检测到清单缺失/损坏时，**自动扫描 meta/ 重建索引**，记录全部找回（按 json 内容恢复状态） |
| 整个 /captures/ 删空 | 目录结构自动重建，计数归零，等同全新卷——记录全丢但系统功能正常 |
| .json 内容被改坏（文件还在但解析失败） | 上传时按普通失败处理，走重试预算，耗尽后进 failed；**不会**自动删除，需 Web 清理 |
| 往卡里放无关文件/照片 | 设备不识别也不清理（数据目录里命名符合 `cap_*` 格式的会被孤儿清扫当作孤儿删掉，其余原样保留）；但它们**占用卷空间**，会推高空间压力，间接导致循环覆盖**提前删除真正的旧记录** |
| 拔卡时机在设备上传中途 | 当次上传 IO 错误按失败重试；重新插卡后自动重新同步卷状态与计数 |

几点提醒：

- 自愈动作发生在**下次 flush / 计数扫描**时，不是实时；休眠中的设备醒来后才会清理。
- 孤儿清扫有双重安全边界：只删"清单确认无主且已存在一段时间"的文件；清单读不出的日期**拒绝清扫**，宁可漏删不可误删。
- **不建议**手工编辑 .json：字段被改坏后记录只会变成 failed 尸体，不会恢复。
- 想安全地手工腾空间：优先删 data/ 里大文件对应记录的整组（meta+data），或直接用 Web 删除。

## 10. 典型配置建议

- **最省电（电池场景）**：批量模式 + 阈值 10 + 循环覆盖 + Flash 上限 32 + 保留时间按需（若只关心最新画面可设小值）。
- **重要记录不丢**：保留时间 72000 + 存满即停 + SD 卡 + 批量/定时模式；需人工关注满仓状态。
- **实时查看**：即拍即传 + MQTT；接受每次唤醒的高耗电。
- **纯本地取证**：仅本地 + SD 卡 + 循环覆盖 + 定期人工导出。
