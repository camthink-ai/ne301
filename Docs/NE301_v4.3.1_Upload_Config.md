# NE301 Capture Upload Service Configuration Guide (v4.3.1)

> Compiled from the current firmware code (`Custom/Services/Upload/upload_coordinator.c`, `Custom/Core/System/json_config_mgr.c`).
> Intended for device operators and maintenance staff: what each configuration item does, where its boundaries lie, and which anomalies may occur and how they self-heal.

---

## 1. Overview

The capture upload service persists every capture (JPEG image + optional inference image + AI result) to disk and uploads it according to the configured mode.

Records live under the `/captures/` tree on the selected storage volume, partitioned by date/hour:

```
/captures/
  ├── meta/<date>/<hour>/cap_*.json   # record metadata (the state field lives in this file; never moved after write)
  ├── data/<date>/<hour>/cap_*_{p,i,a} # payload files: p=primary image, i=inference image, a=AI result
  └── index/<date>.idx                # daily manifest (append-only index with tombstone entries)
```

**pending / sent / failed / local are states stored as a field in the metadata JSON, not four directories** — a state transition only rewrites the `state` field in the meta JSON and appends an entry to the index; files themselves never move.

Each record has a unique ID (`cap_<timestamp>_<seq>`). State transitions:

```
pending ──upload success──> sent ──(past retention)──> deleted
   │
   └─retries exhausted / retry disabled──> failed ──(manual retry via Web)──> pending
```

## 2. Configuration Overview

| Item | Range | Default | Purpose |
|---|---|---|---|
| Upload mode | instant / batch / scheduled / local-only | instant | When uploads happen after a capture (see §3) |
| Storage location | auto / internal flash / SD card / none | auto | Which volume records are written to (see §4) |
| Storage policy | wrap-around / stop-when-full | wrap-around | Delete oldest or reject new captures when full (see §4.3) |
| Flash record cap flash_max_records | 16 – 256 | 32 | Total record count cap across all states on the internal flash volume; oldest deleted when exceeded (flash only; SD has no count cap) |
| Upload protocol | MQTT / WebHook | MQTT | Channel used for uploads |
| Batch threshold batch_count | 2 – 20 | 10 | In batch mode, one upload pass is triggered when pending count reaches this value |
| Schedule nodes | up to 8; the web UI only offers half-hour granularity (xx:00 / xx:30); the API accepts any minute (0–1439, invalid values reset to 0) | none | In scheduled mode, uploads trigger at these times of day |
| Retention keep_sent_hours | 0 – 72000 hours | 72000 (forever) | How long sent (uploaded) records are kept; 72000 = keep forever, 0 = delete immediately after upload |
| Auto retry retry_enable | on / off | on | When off, the first failure goes straight to failed with no automatic retry |
| Retry attempts retry_max_attempts | ≥0, 0 = unlimited | 5 | Per-record automatic retry cap |
| Upload network upload_comm_type | follow system / specific network | follow system | **Low-power wake captures only**: the preferred network to bring up on wake; runtime captures always use the system's current network |

> Note: the `max_pending_records` field exists in the config and API but is not enforced by the current firmware; it is not covered in this document.

## 3. Upload Modes

### 3.1 Instant

- Upload completes **synchronously inside the capture call** before returning; a success return means "sent or queued for retry".
- **Does not depend on local storage**: even if storage fails (volume full / no card / persist error), the image is uploaded directly from RAM and is not lost.
- On upload failure the record stays in `pending` awaiting later retry; with storage set to "none", failure is final.
- **Highest wake power draw**: every capture wake requires the network — the only mode that always brings it up.

### 3.2 Batch

- Captures are only persisted and the device sleeps immediately — **no network**, making this the most power-efficient mode for low-power use.
- Upload triggers when the pending count (failed excluded) reaches `batch_count`; only the wake that reaches the threshold brings up the network for a bulk upload.
- The threshold is evaluated **after the new capture is added** (pending+1 ≥ batch_count), so a single batch may contain up to batch_count + 1 records (leftovers + the new one).
- If the network stays unavailable, pending keeps accumulating; each wake only persists.

### 3.3 Scheduled

- Captures are only persisted; at the configured daily schedule nodes (up to 8) the device wakes and uploads **all** pending records.
- Nodes are expressed as minutes-of-day (0 = 00:00, 1439 = 23:59); invalid values reset to 0.
- **The web UI only offers half-hour granularity** (xx:00 or xx:30; new nodes default to 08:00); the API accepts any minute.
- **Frequency cap = 8 times per day**: the node count caps at 8, so requests like "upload once per hour" cannot be met in scheduled mode — use batch mode with a threshold instead.
- With no nodes configured, this mode effectively never uploads automatically (only manual web triggers/retries).
- Unlike batch mode: each scheduled node **fully drains** pending regardless of backlog size.

### 3.4 Local-only

- Persists into `local` state only; never uploads, never flushes.
- Needs no network on wake; records can only be viewed/downloaded/deleted via the web.

### 3.5 Wake network-bring-up rules (needs_network)

On a low-power wake, the system decides *before* service start whether this wake needs the network, avoiding a multi-second bring-up for nothing:

| Mode | Brings up network? |
|---|---|
| LOCAL_ONLY | never |
| INSTANT | every wake |
| BATCH | only when this capture reaches the batch threshold, or there are failed records worth retrying |
| SCHEDULED | only when a schedule node is due, or there is pending/failed backlog |

> `failed` records **do not count** toward the batch threshold — a pile of failed records will not wake a batch-mode device; only a manual web retry or (in scheduled mode) a due node handles them.

**Boot-time catch-up**: the table above only constrains the low-power wake path. On a normal runtime boot the network services start anyway, and the upload service fires **one unconditional sweep** after start — it waits for the channel to become ready (up to 30 s), then uploads all pending records regardless of the current mode (local-only naturally idles since it has no pending). Leftovers from a mode switch and backlog accumulated while offline are therefore drained automatically on the next networked boot. If the broker is not connected within 30 s of boot, this sweep is skipped until the next upload trigger.

## 4. Storage Location and Policy

### 4.1 Storage location

| Location | Description |
|---|---|
| Auto (default) | Chosen at boot from SD card presence: card present → SD, absent → flash. Runtime hot-plug tracking: upgrades to SD on the next record operation after insertion; downgrades back to flash after removal |
| Internal flash | Fixed on-chip littlefs volume. Small capacity, subject to the `flash_max_records` count cap |
| SD card | Fixed SD volume. No count cap, bounded only by card capacity. With no card present, captures take the storage-failure path |
| None | Records are not persisted. In instant mode this equals "upload only, no archive"; other modes fail the capture outright |

**Auto-mode boundaries**:

- Selection is based on **card-detect** (non-blocking) and does not wait for the mount; before an actual persist there is a bounded 3-second SD readiness wait (5 ms polling) — on timeout the capture takes the storage-failure path. There is **no silent fallback to flash**, so one batch never scatters across two volumes.
- The choice is re-resolved on every wake: mid-run insertion/removal and card swaps across sleep cycles take effect by the next wake at the latest; a single inconsistent state during a swap self-corrects in the following cycle.
- Record counts and the index are bound to their volume: after a volume switch the two volumes' records are independent, and the web list shows the currently active volume.

### 4.2 Flash record cap

- `flash_max_records` (16–256, default 32) caps the **total record count across all states** (pending+sent+failed+local) on the flash volume.
- When exceeded, the wrap policy deletes the oldest records to make room.
- **Boundary**: the count cap is only armed while space remains on the volume. If free space runs out first, **space-based cleanup** takes over (also deleting oldest); the actual count may then sit below the cap. SD is unaffected by this setting.

### 4.3 Storage policy (what happens when full)

| Policy | Behavior |
|---|---|
| Wrap-around (default) | When full, oldest records are deleted automatically to make room and new captures proceed. Deletion order: **sent → local → failed → pending** (uploaded records first, unsaved-for-upload last), oldest first within each state |
| Stop-when-full | When full, old records are kept and new captures are rejected outright |

**Stop-when-full × mode behavior**:

- Instant: **unaffected** — after the storage rejection it still uploads directly from RAM (nothing saved).
- Batch / scheduled / local-only: the capture fails outright (no-space error).
- **Self-healing**: on rejection, one bounded sweep of over-retention sent records runs — if retention is not set to forever, expired sent records are purged and the freed space or count lets the **next** capture succeed (at most one capture lost at the boundary). With retention at 72000 (forever) nothing is purged: rejection continues until records are deleted manually or the configuration changes.

### 4.4 Retention (keep_sent_hours) and cleanup timing

- Applies only to **sent** (uploaded) records; pending/failed/local are never time-deleted.
- `72000` (default) = keep forever; `0` = delete immediately after upload (equivalent to "stream, don't archive").
- **Shrinking the retention cleans existing over-age records immediately** (at the next cleanup opportunity), including history on a **newly inserted SD card** — swapping cards is no exemption.
- Cleanup runs inside the flush flow when the upload channel is ready (including the idle path with nothing pending); it **does not run while the channel is down** (network unreachable / service disabled). A forever-retention device that never connects therefore keeps its sent records — expected behavior.
- Each cleanup round is time-budgeted (15 s); very large backlogs complete over multiple rounds.

## 5. Retry and Failure Handling

- With automatic retry **off**: the first failure goes straight to `failed`; only manual web retry remains.
- With it on: a record moves to `failed` after `retry_max_attempts` retries (0 = unlimited).
- `failed` is a **terminal state**: it never returns to pending automatically and is not cleaned by retention; it only occupies space. Recovery is only via manual web retry (single or all).
- Records whose source image file is lost/corrupted are marked failed outright (without consuming retry budget) so they cannot hang in pending forever.
- Records with missing metadata (e.g. a partial record left by power loss) are self-healed to a tombstone in the index and skipped without blocking the upload loop.

## 6. Upload Protocols

| Protocol | Channel-ready condition | Notes |
|---|---|---|
| MQTT | service running **and** broker connected | Large flushes use a sliding window (window = batch_count, cap 16); failures retry |
| WebHook | webhook service enabled | Sequential POSTs; state semantics identical to MQTT (success → sent, failure → retry rules) |

While the channel is not ready (network down, service disabled, broker disconnected), the flush pass is skipped entirely — no idle spinning burning IO and battery; pending stays backlogged until the next trigger.

## 7. Boundaries and Limitations (important)

1. **Flush time budget**: computed from the backlog (≈3 s per record + 3 s base), **capped at 30 s per pass**. Larger backlogs continue in later passes (scheduled mode waits for the next node; batch mode for the next threshold or manual trigger).
2. **Sleep cut-off and duplicates**: records in flight inside the sliding window (≤ window cap of 16) that are cut by a sleep are re-published on the next pass — receivers may see a **small number of duplicate** messages and must deduplicate by record ID. This trades bounded duplicate risk for bounded wake duration.
3. **Scope of `upload_network`**: it only affects which network is preferentially brought up for **low-power wake captures**; runtime captures (device already booted and working) always use the system's current network. Pointing it at an unconfigured network means wake captures cannot upload.
4. **Time-sync dependency**: schedule nodes and retention cleanup both require a correct system clock. Before the clock is calibrated (first boot without SNTP/U0 time sync), scheduled uploads do not fire and time-based deletion is unreliable.
5. **Slow SD mount**: a bounded 3-second wait before persisting; on timeout the capture takes the storage-failure path (see §4.3) and never blocks the wake indefinitely.
6. **Failed backlog does not wake the network** (batch mode): by design, a pile of dead records must not repeatedly drag the device out of sleep; the cost is that batch-mode failed records need manual handling on the web.
7. **Instant's final failure**: with storage "none" and an upload failure, the record is dropped entirely (nowhere to persist for retry).

## 8. Common Anomalies and Self-healing

| Symptom | Cause | Self-healing / action |
|---|---|---|
| Batch-mode pending keeps growing, nothing uploads | Network unreachable / broker disconnected / MQTT service not running | Drained in bulk when the channel recovers at the next threshold or next boot; records are not lost meanwhile |
| Batch/scheduled captures fail after stop-when-full | Volume full or flash count cap reached | If retention is not forever: over-age sent records are purged automatically and the next capture recovers; otherwise delete manually or adjust the config |
| Fewer sent records than expected | Retention is 0 (delete on upload) or records aged out | Expected per configuration; set 72000 to keep forever |
| Old records "disappear" after swapping SD cards | Auto mode volume switch; the web shows the active volume only | The other volume's data is intact; switch the storage setting to view it. Note the new card is cleaned per current retention |
| Records stuck in failed | Retries exhausted, source image damaged, payload over limit, etc. | Retry single/all from the web; delete unrecoverable ones |
| Occasional duplicate messages on the receiver | Re-publishing of the in-flight window after a sleep cut | Deduplicate by record ID |
| Scheduled uploads never fire | No nodes configured / clock uncalibrated / mode not scheduled | Check configuration; effective at nodes once time sync completes |
| First capture after wake occasionally lost | SD mount slower than the 3 s wait (and stop-when-full boundary loss of one record) | Bounded loss; instant mode is unaffected (direct RAM upload) |

## 9. What Happens If /captures/ Is Hand-Edited

The internal flash volume is not externally accessible; the realistic scenario is **pulling the SD card and editing it on a PC**. The index is the single source of truth for enumeration, and after external additions/deletions the device self-heals as follows:

| User action | Device behavior |
|---|---|
| Delete image files under data/ (meta intact) | On upload the record is judged "source missing" and **goes straight to failed** (retry budget not consumed — retrying is pointless); visible in the web list and deletable. Occupies count, not space |
| Delete a .json under meta/ (data files intact) | The index entry goes stale: **tombstoned** at the next flush (excluded from counts/lists); leftover data files are gradually reclaimed by the orphan sweep. **Fully self-heals** |
| Delete .idx files under index/ (or corrupt them) | On the next boot the missing/damaged manifest is detected and the **index is rebuilt by scanning meta/**, restoring all records (states recovered from the json contents) |
| /captures/ wiped entirely | Directory tree rebuilt automatically, counts reset — equivalent to a fresh volume: all records lost but the system stays functional |
| .json content damaged (file present but unparseable) | Treated as a normal upload failure, consumes the retry budget, ends in failed; **not** auto-deleted — clean up via the web |
| Drop unrelated files/photos onto the card | Not recognized or cleaned by the device (files matching the `cap_*` naming in the data dirs are reaped as orphans; everything else is left untouched); they **occupy volume space**, raise space pressure, and indirectly cause wrap-around to **delete real old records earlier** |
| Card pulled mid-upload | IO errors on that upload are retried as failures; the volume state and counts re-sync automatically on re-insertion |

Notes:

- Self-healing happens at the **next flush / count sweep**, not in real time; a sleeping device cleans up only after waking.
- The orphan sweep is double-bounded: it only deletes files "confirmed ownerless by the manifest and not freshly written"; dates whose manifest cannot be loaded are **refused** — better to leak than to destroy a live record.
- **Do not** hand-edit .json files: once fields are damaged the record only becomes a failed corpse and will not recover.
- To free space by hand safely: delete the full group (meta+data) of the records behind the big data/ files, or just use the web delete.

## 10. Typical Configuration Recipes

- **Most power-efficient (battery)**: batch mode + threshold 10 + wrap-around + flash cap 32 + retention as needed (a small value if only the latest footage matters).
- **No important records lost**: retention 72000 + stop-when-full + SD card + batch/scheduled mode; monitor fullness manually.
- **Real-time viewing**: instant + MQTT; accept the high per-wake power draw.
- **Pure local forensics**: local-only + SD card + wrap-around + periodic manual export.
