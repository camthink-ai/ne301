## 变更概要

v4.3.1 是自 v2.1.0 以来规模最大的一次发布：Flash 分区与内存布局重构、WiFi 主机栈整体迁移、全新的抓拍上传系统与整合包一键升级，并伴随大量现场稳定性修复。以下为最重要的变更点，细化说明见后续章节。

### 重点新功能

1. **整合包一键升级（OTA Bundle）** — `make pkg-bundle` 将全部固件打成一个包，Web 端一次上传即可完成整机升级：包内自带分区表支持布局迁移，同版本条目可勾选跳过，跨型号固件包被硬拒绝，FSBL 载荷先暂存校验再写入。后续整机升级（包括分区表变更场景）不再需要逐个固件手动处理。
2. **WiFi 子系统全面升级** — 主机驱动迁移至 WiseConnect 4.1.1 SDK；新增 WiFi 固件 OTA 升级（配套固件 `2.16.5.108`，版本不匹配自动引导）；WiFi 国家码设置（us / eu / jp / kr / cn）；AP 侧自建 DHCP 服务器（粘性租约）；以及 Si91x SPI 总线与主机栈的一系列稳定性加固。
3. **抓拍上传管道** — 全新端到端抓拍-上传系统：四种上传模式（即时 / 批量 / 定时 / 仅本地）、MQTT 批量发布与 Webhook 投递、低功耗唤醒调度、SD 热插拔自动切换、Web 记录管理界面。
4. **HaLow (802.11ah) 完整支持** — mm6108 / mm8108 双芯片构建切换、射频参数与扩展国家码 Web 配置、省电模式 Web 开关（默认关闭，动态 PS timeout 配对生效）。
5. **Web 管理界面大改版** — Web 资源独立分区，损坏时自动进入内置 Web Recovery；新增文件管理（Flash / SD）与固件升级中心（APP / Web / 模型 / FSBL / WiFi / 整合包 + 期望版本校验）；连接与实时推流稳定性大修。
6. **AI 与模型** — STEdgeAI 2.2 / 3.0 / 4.0 运行时编译期统一切换（本发版线为 4.x）；AI 分区扩至 8MB A/B 双槽；新增姿态估计、指针仪表读数、实例分割、BlazeFace 人脸检测等模型能力。

### 重点修复

1. **Web 实时预览晚连黑屏** — 编码器每会话仅发送一次 SPS/PPS，晚连客户端永久黑屏；现按客户端做关键帧同步。
2. **视频管道停止死锁** — `video_pipeline_stop()` 无限等待阻塞的节点线程并持锁卡死 HTTP 任务；现 3 秒上限 + 强制回收。
3. **Web 连接与推流稳定性大修** — 单次请求连接、静态资源 etag/304 缓存、视频帧 FIFO 复制、WS 发送缓冲上限，消除手机链路 `err_network` 弹窗与花屏。
4. **启动决策定时器线程栈溢出** — 启动超时回调运行在微小的 ThreadX 定时器线程上，printf/LOG 即栈溢出 HardFault；决策移至独立大栈线程。
5. **Flash `stat` 未设置 `st_mode`** — 恒为 0 导致内部 Flash 上目录检测、删除/状态检查全部失效。
6. **JPEG 编码尾部截断** — 修复 DMA 填充/EOI 截断导致的浏览器预览底部马赛克、整图渲染不全。
7. **XSPI 擦除忙等饿死看门狗** — 4K NOR 擦除在无让出的紧凑就绪轮询中自旋 45-200ms；实时优先级 web 任务调用下把看门狗任务饿过 16s IWDG 窗口——无声复位、无任何日志。就绪轮询现周期性让出。
8. **RTMP 每帧末尾 NAL 截断** — 起始码扫描边界少查 3 字节，每帧推流丢失 slice 最后 3 字节（约 0.4% 帧出现底行宏块错误）；修复后 0 解码错误（对照未修复机同窗口 4027 行）。
9. **RTMP 推流从不自动启动** — `rtmp_enable` 只被持久化、从不执行，每次重启后推流一直空等外部 `start` 调用（每次损失约 6 分钟录像）；现站点链路就绪后自行启动推流。
10. **摄像头缓冲竞争与编码器冷启动全 INTRA 锁死** — DCMIPP 仍在 DMA 写入的缓冲被发布（撕裂帧）；编码器首帧失败后每帧被强制全 INTRA、重初始化也无法逃逸（现通过 QP 地板步进自动逃逸）。

## ⚠️ 破坏性变更 (BREAKING CHANGES)

### 1. Flash 分区表重新设计

Flash 分区布局进行了重构，**新版本 Web 固件必须重新上传**，旧版 FSBL 和 WiFi 固件版本不匹配时系统会弹出提示。

| 分区       | 旧版本 (v2.1.0)         | 新版本 (v4.3.1)          | 变更说明                    |
|-----------|------------------------|-------------------------|----------------------------|
| AI_1      | 5MB @ 0x70E00000       | 8MB @ 0x70900000        | 地址前移，大小翻倍（合并原 AI_DEFAULT） |
| AI_2      | 5MB @ 0x71300000       | 8MB @ 0x71100000        | 地址前移，大小翻倍（合并原 AI_3） |
| AI_DEFAULT | 5MB @ 0x70900000      | — 已移除 —              | 合并至 AI_1                 |
| AI_3      | 8MB @ 0x71800000       | — 已移除 —              | 合并至 AI_2                 |
| WEB       | — 不存在 —             | 1MB @ 0x71900000        | **新增** Web 独立分区         |
| WiFi FW   | 4MB @ 0x77C00000       | 3MB @ 0x71A00000        | 地址前移，大小调整             |
| LittleFS  | 64MB @ 0x72000000      | 32MB/96MB @ 0x71D00000  | 地址变更并支持 64MB/128MB Flash，首次开机重格式化；普通抓拍不存于此，但 MQTT TLS CA/客户端证书/私钥文件会丢失，NVS 与 SD 数据保留 |
| Reserve2  | 28MB @ 0x76000000      | 3MB @ 0x73D00000/0x77D00000 | 地址和大小变更            |

### 2. PSRAM 内存布局变更

- **APP 固件 PSRAM 启动**：移除条件编译，PSRAM 启动成为唯一方式，APP 可用空间从 4032K 扩大至 4096K
- **PSRAM SWAP 区域删除**：位于 `0x903F0000` 的 64KB PSRAM SWAP 区域已删除
- **新增 SRAM_POOL 区域**：`0x34000000-0x341B1FFF` (1736K)，原 SRAM APP 空间转为内存池
- **UNCACHED 区域调整**：起始地址从 `0x341A0000` 移至 `0x341B2000`

### 3. WiFi 固件升级（必需）

- SiWG917 无线固件升级至 **`SiWG917-B.2.16.5.1.0.8`**（编码 `2.16.5.108`），配套新 SDK
- 旧版 WiFi 固件（如 `2.14.5.x`）仍可正常使用，但未升级到期望版本前设备会持续提示
- 新增 `EXPECTED_WIFI_VERSION` / `EXPECTED_FSBL_VERSION` 编译期版本校验机制

## 新功能（细化）

### 整合包一键升级（OTA Bundle）

一次上传完成整机固件升级，特别覆盖"分区表变更"场景（旧固件无法把新固件烧到新地址的问题）。

- **打包**：`make pkg-bundle` 产出 `ne301_Full_v<版本>_bundle.bin`——4KB 外层头（子固件清单 + 新分区表）+ 既有各 `_pkg.bin` 按烧录顺序（模型 → Web → WiFi → APP → FSBL）串联，内层包格式不变，CI 同步产出 bundle 产物
- **入口**：系统设置 → 固件升级 → 导入固件 → 高级选项 → **整合包一键升级**（`/import-bundle`）
- **预检计划表**：选择文件后设备解析包头并比对本机分区表 / 版本，返回烧录计划（类型 / 版本 / 目标地址）；**同版本且分区未移动的条目可勾选跳过**（设备端二次校验，不允许全部跳过；跳过 WiFi 同时撤销推送标志，避免陈旧固件被推送）；FSBL 仅在分区表完全未变时可跳过；**变更分区表的整合包必须包含 FSBL**，否则预检拒绝
- **统一强制直烧**：按整合包自带分区表地址直接烧录（不走 AB 槽位）；会话开始即擦除 OTA info，重启后按新布局自动重建 SystemState
- **分区表漂移警告**：每个单固件包在 OTA 头记录构建时分区表 CRC，与运行固件不一致时所有单固件升级页弹出警告对话框（可选择继续，或改走整合包完成分区迁移）
- **设备型号门禁**：OTA 包头记录 `device_model`（NE301 = 0x3010，未标注的旧包放行），预检与上传双重校验，跨型号固件包（如 NE302 的包装到 NE301）被硬拒绝；根 Makefile `DEVICE_MODEL` 为唯一来源
- **烧录保护**：FSBL 载荷先暂存 PSRAM、CRC 校验通过后再写入；OTA 上传期间刷新 AP 休眠定时器，低功耗模式不会在烧录中途睡眠
- **前端烧录护盾**：烧录期间路由阻止 + `beforeunload` + 全屏遮罩三重防止误离开；进度停滞 >4s 时显示"分区擦除中"提示（8MB AI 分区擦除需数秒）；完成后展示结果页，设备失联时引导至等待页
- 设计文档见 `Script/docs/NE301_OTA_Bundle_Design_EN.md`

### WiFi 固件 OTA 升级

- 新增 WiFi (SiWG917) 固件的 OTA 升级支持，通过 Web 界面或系统设置上传并更新
- **两阶段升级流程**:
  1. **上传阶段**: 流式写入 Flash (`WIFI_FW_BASE`)，写入 `flash_header_t` + `.rps` 固件本体，OTA 包头仅用于 Web 端校验不写入 Flash
  2. **确认阶段**: 设置 NVS `wifi_mode=update` 标志，设备重启后由 `firmware_upgrade_from_flash()` 将 `.rps` 推送至 SiWG917 芯片
- **WiFi 版本检测与提示**: 系统同时读取 Flash 中存储的 WiFi 固件版本和芯片当前运行版本，在固件升级页面展示并自动检测版本不匹配
- **期望版本校验**: 当 Flash 和运行版本一致但与期望值不同时，Web UI 将弹出引导升级对话框
- **升级等待页**: WiFi 固件推送至芯片耗时较长（约 1-3 分钟），前端在重启后轮询设备状态，超时后跳转至 LED 指引等待页 (`/upgrade-waiting`)
- `firmware_upgrade_from_flash()` 与 WiFi 固件 Flash 头读取均持 storage 锁保护，避免与文件系统并发访问冲突（含 XIP 内存映射禁用窗口）；各错误路径均正确释放资源
- 按触发来源选择固件源：**Web OTA 用 Flash，recovery/CLI 用 SD 文件**（SD 上一份杂散固件不再会劫持 Web 上传的固件）
- 新增 `wifi_mark_update_pending()` / `wifi_get_running_version()` / `wifi_get_flash_version()` 接口

### WiFi 主机 SDK 升级 (WiseConnect 4.1.1)

- WiFi 主机驱动移植到厂商 **WiseConnect 4.1.1 SDK**（`SiliconLabs_SDK_4_1_1`，旧版 4.0.2 保留用于回退）。SiWG917 芯片固件不变，仍为 `2.16.5.1.0.8` —— 本次仅为主机侧 API 迁移，非固件升级。
- HAL 适配新 SDK：`sli_si91x_driver_send_command` → `sli_wifi_send_command`、`sli_si91x_host_free_buffer` → `sli_buffer_manager_free_buffer`；NCP 主机改为 `rx_irq`/`rx_done` 总线模型，唤醒改为直接读取 GPIO（旧 `sem_sta` 获取会卡住每次 SPI 事务）。
- **修复 EXTENDED 扫描 HardFault**：固件逐 AP 以 beacon 形式上报（`result != NULL`，自动累积进 SDK 数据库），仅空载荷事件表示扫描完成。新增 guard 跳过中间 beacon，AP/STA 恢复只执行一次 —— 此前扫描中途反复 up 导致 `0x19` busy → HardFault。
- **TWT 自动选择**改用公开 v2 API（支持同步/异步 AP 协商等待）；`low_power_mode_ctrl` 改为接收完整配置（profile/dtim/monitor/beacon-miss），新增 CLI `twt`、`lpwr` 命令。
- **主机总线与驱动层加固**（随迁移一并完成）：`ulp_wakeup_init` 由无限循环改为有界重试、失步轮询定期 `osDelay` 让出 CPU、host SPI 传输统一经互斥锁 + DMA 安全静态缓冲、片选由外设 NSS 驱动、连续 0x19 TX 失败自动升级为固件错误恢复、SDK 断言接入 fault-safe 恢复路径——总线失步或固件管道卡死不再静默挂死整机。
- 配置重置后 AP SSID 为空时自动生成 `NE301_<mac>` 默认名。

### WiFi 国家码 (Region Code)

- 新增 `sl_net_wifi_set/get_region_code` 及索引/支持数量辅助接口，支持 **us / eu / jp / kr / cn**
- 在下一次 `sl_wifi_init` 时应用；设置前要求两个 netif 均 DEINIT；`wifi_country_code` 持久化到 NVS
- 通过 Web API + WiFi 区域设置界面暴露
- 显式排除 `WORLD_DOMAIN`（在 CONCURRENT_MODE 下会使 AP 初始化失败 0xF）

### AP 侧自建 DHCP 服务器（粘性租约）

- 用 host 侧 lwIP 实现替换 Si91x 固件 DHCP 服务器，AP 运行自己的服务器并获得稳定寻址
- **粘性租约 (sticky lease)**：站点断开后仍缓存 MAC→IP 绑定，重连时拿回原地址；表满时按 LRU 淘汰最旧的缓存条目，活跃客户端永不淘汰
- 租约表用互斥锁保护（tcpip 线程 vs WiFi 事件上下文）；健壮的选项解析（PAD 处理、边界检查），回复填充到 RFC 300 字节下限
- netif（双栈）：关闭 NWP 固件 DHCP 特性位，AP up 时启动 host dhcpserver；站点 join/leave 时注册/注销
- **旧固件兼容（< 2.16.5）**：一次性固件版本检查，老固件无 host DHCP 与 `IP_ADDRESS_INFO` notify 时自动回退固件 DHCP 服务器

### HaLow (802.11ah) 支持

- HaLow Wi-Fi 完整集成：快速连接、运行时射频同步、重连 IP 修复
- 扩展 RegDomain 国家码支持（端到端）；PKA 加密硬件卸载；IP 配置持久化存储；SPI6 时钟自适应、放宽 EU 占空比限制
- **mm6108 / mm8108 双芯片支持**：构建期通过 `HALOW_CHIP` 选择目标硅片（默认 `mm8108`）：`make`（mm8108）或 `make HALOW_CHIP=mm6108`。芯片结构、固件 blob、BCF 配置均由宏门控；两套固件共存，未选中的那套由 `--gc-sections` 丢弃
- **与 PoE / 4G 的硬件互斥**：PoE(W5500 INT=PD15) 与 HaLow(BUSY=PA15) 共用 EXTI15 中断线，硬件上二选一；HaLow 与 4G 亦冲突，PoE 与 4G 可共存。软件强制互斥——切换或启动某条链路时自动停用冲突链路，启动时仅在 PoE/HaLow 中二选一初始化（PoE 优先，除非首选 HaLow），deinit 时清空 shim IRQ 回调避免边沿串入对方协议栈。
- **省电模式 Web 配置**：HaLow 芯片 PS 暴露为射频设置开关（**默认关闭**），NVS 持久化、开机同步、JSON 导入导出；每次设置 PS 均配对 `mmwlan_set_dynamic_ps_timeout`（timeout 为独立固件参数，不配对会出现"开启 PS 却不睡"的假象）；SDK 侧恢复官方省电默认值，运行时行为完全由应用层配置控制
- Web UI 支持 HaLow 网络配置（射频参数 / 国家码 / 省电开关，中英双语）

### Web Recovery 恢复系统

- 新增 `web_recovery` 模块：Web 固件分区为空或损坏时自动进入内置恢复页面
- 恢复页为编译在 APP 固件中的自包含 HTML 页面（无外部资源依赖），提供 Web 固件上传功能
- Web 固件上传成功后自动调用 `web_recovery_reload_assets()`，从 Flash 重载 assets 并退出恢复模式，**无需重启设备**

### Web 端固件版本管理增强

- 固件升级页面大改版：
  - 导入固件对话框支持 APP / Web / AI 模型 / 设备配置文件
  - 高级选项菜单提供独立的 FSBL 升级、WiFi 升级与**整合包一键升级**入口
  - 新增 WiFi 固件升级独立页面 (`/import-wifi`)、整合包升级页面 (`/import-bundle`)
  - 固件信息页展示全组件版本：APP / Web / AI 模型 / FSBL / WakeCore / WiFi
- **FSBL / WiFi 期望版本校验**: 编译时指定期望版本，Web UI 自动检测并弹出升级引导

### AI 分区重构与 STEdgeAI 4.x 运行时

- `FIRMWARE_DEFAULT_AI` 重命名为 `FIRMWARE_AI_2`，保留 `FIRMWARE_AI_1`，支持 AI 模型 A/B 双槽切换；AI 分区大小从 5MB 增大至 8MB
- **统一 STEdgeAI 2.2 / 3.0 / 4.0 运行时编译期切换**: 应用代码共享，通过 `STEDGEAI_VARIANT` 选择版本。`stedgeai.mk` 自动选取对应 NPU 运行时库、设备和额外源文件。固件与模型包必须使用相同变体
- **生成 `stedgeai_version.h`**: `MODEL_STEDGEAI_VERSION_SUPPORTED` 改为生成的版本头文件，替代 `-D` 编译器传参。`-MMD` 依赖追踪可正确检测变体变更 — 切换变体不再需要 `make clean`

### AI 与模型

- YOLOv8-Nano / YOLO11n-Nano 人体姿态估计 (4 关键点)
- 指针仪表读数: YOLOv8-pose 4 关键点 → 百分比读数转换
- 实例分割 (ISEG): YOLOv8 模型集成
- BlazeFace 人脸检测: 128×128 分辨率
- 可配置 AI 推理频率
- 连续 AI 结果遥测：支持 CBOR 精简格式、仅元数据模式
- SPE 结果处理：`overlay_results` 门控

### 抓拍上传管道

全新的端到端抓拍-上传系统,按日期分层存储记录 (`/captures/{meta,data,index}/<日期>/`),存储位置可在 Flash / SD 卡之间选择(支持 auto / flash / sd / none)。
- **四种上传模式**:
  - **即时 (Instant)** — 抓拍即同步上传;失败则记录留在 `pending/` 自动重试
  - **批量 (Batch)** — 先持久化,待待传数量达到设定阈值或下次唤醒节拍时统一上传
  - **定时 (Scheduled)** — 在设定的每日时刻统一上传
  - **仅本地 (Local-only)** — 仅存储到本地,永不上传
- **间隔抓拍运行在配置锚定的每日网格上**:抓拍节点为 `start + k × interval_sec`,窗口为**闭区间** `[start, end]`(恰落在结束时刻的节点会拍摄)。普通间隔模式以日内时刻为锚点覆盖全天、节点连续排过午夜;定时间隔模式窗口从 `start_time` 跑到 `end_time`(结束早于起点即跨零点,全天 = 任意起点 `T` 配 `T−1分钟`,定时模式拒绝 `end_time == start_time`)。唤醒、上传清空与重启都不会重定网格基点;睡眠时长精确对齐下一个节点,关窗夜间一觉睡到次日窗口起点,不再每间隔空醒一次。从未存过 `end_time` 的旧配置首次开机时一次性迁移为全天窗口(有日志标记)。
- **MQTT 批量发布管道 + Webhook** 投递支持；MQTT 发布载荷超过 1800B 直接拒绝，规避芯片侧 CE_TX 缓冲溢出导致的共享堆损坏
- **可配置最大重试次数**;失败记录可在 Web UI 单条重试或一键全部重试
- **存储策略 (WRAP / STOP)** 配合自动清理;Flash 记录上限可配置 **16~256 条,默认 32**(NVS `cu_fl_max`,经 Web 上传配置 API 暴露;0/越界回退默认值)——上限按所有状态计数,更低的默认值同时约束新设备冷启动全树扫描时延与平均功耗。SD 卡无条数上限
- **低功耗唤醒调度**:抓拍与上传清空共用单一调度器,支持闹钟覆盖;唤醒时仅拉起配置的上传网络接口(省去多秒网络初始化、省电);休眠前等待正在进行的上传完成再断电
- **网络 fail-fast**:某次唤醒不会上传任何内容时,完全跳过整套网络协议栈
- **Web 管理界面**:抓拍设置页(配置 + 记录双标签)、批量选择/删除/重试、时间范围筛选、新旧排序、上传网络选择器(默认或指定接口)
- **NVS 持久化配置** + REST API（上传配置、队列状态、记录查询、删除/重试和批量操作）
- 存储性能优化以保持抓拍/上传热路径高效:`lfs_fs_size` 结果缓存、stat 优先于 mkdir、轻量挂载检查
- **SD 热插拔自动切换 (auto 模式)**:抓拍与状态路径实时跟踪 SD 插拔,无需任何 Web 请求即可切换存储目标;`storage_full` 按卷记录并对照实时空闲空间,删除文件后自动清除陈旧满盘横幅
- **keep_sent_hours 支持永久保留**:上限提升至 **72000 (= 永久保留)** 且为新默认值——记录仅在满盘或达到记录数上限时才删除;`0` 维持原语义(上传成功即删)
- **计数缓存与日索引紧凑化**:记录计数在 count/状态/flush 预算各路径共享同一份 RAM 缓存(变更即失效,冷启动仅一次全量扫描);日索引原始条目 ≥64 且死条目达 4 倍时在加载时重写为仅存活条目(无存活条目则移除),由独立 idx 互斥锁保护
- **大记录集正确性与 records API 分页**：日期枚举改为动态扩容，可覆盖超过 128 天的记录；单日清单超过 4096 个唯一记录 ID 时哈希表按需扩展；状态转移通过临时文件与原子重命名替换元数据，清单追加失败时会明确报错，格式错误或混用旧格式的清单会被拒绝而不会被当作有效记录读取；records 分页使用多取一条的 lookahead。因此末页 `total` 为精确值，仍有更多记录时则是 `offset + records.length + 1` 的下界，避免昂贵的全树计数
- **批量拉网为纯阈值判定** (`pending+1 ≥ batch_count`):failed 记录不会唤醒网络,仅支持 Web 手动重试;`retry_enable` 关闭时首次失败直接进终态 failed,开启且 `retry_max_attempts = 0` 时不限次重试

## 修复（细化）

### 网络 / PoE

- **启动连接决策移至独立大栈线程**：启动超时定时器回调运行在微小的 ThreadX 定时器线程上，任何 printf/LOG 都会栈溢出并 HardFault。现改为定时器仅置事件标志，决策/连接在专用大栈线程上执行
- **AP 启动不再受蜂窝状态门控**：移除蜂窝活跃时跳过 AP 的分支，AP 拉起不再被 4G 状态阻塞
- **上行链路断开时重置 DNS 服务器**：lwIP DHCP 客户端（WiFi / PoE / HaLow）与 PoE 静态配置会把当前网络的 DNS 写入全局解析器且从不清除，切换网络后旧网络的 DNS 仍在生效——在新网络中不可达。上行断开/去初始化时恢复开机默认值；每条上行连接时重新建立 DNS（DHCP 重新学习、PoE 重新应用 NVS 配置）
- **iperf 挂死**：TCP 阻塞发送加 `so_sndtimeo` 上限，消失的对端不再把任务拖过 `-t`/`-x`;ETIMEDOUT 按可重试处理;`-t` 截止在部分写循环内强制执行;`-x` 停止从任意非空闲状态幂等

### 无线 (WiFi)

- **LED 指示灯设备名纠正**：`wifi_update_process` 由 `IND_DEVICE_NAME` 改为 `IND_EXT_DEVICE_NAME`，与 `device_service` 实际使用的 LED 设备一致
- **启动 AP 状态竞争**：`device_service_start` 此前设了一个盲目的 ap-off，与异步 netif 线程上 `on_wifi_ap_ready` 的 ap-on 竞争。改为依据实际 AP 状态设置启动指示，不再覆盖已 up 的 AP
- MQTT client-id 哨兵 `AICAM-000000` 改为在 `mqtt_build_topics` 中以 MAC 后缀重写（原时间戳方案不可靠）
- 按接口设置 netif flags：AP 不再设置 `NETIF_FLAG_IGMP`
- 连接失败时调用 `sl_wifi_disconnect` 复位链路；`nm_get_netif_list` 取反正数 `sl_status`，避免被误读为计数
- eth_wan 默认接口：修复无蜂窝模块时的默认值处理

### 文件管理 / 存储

- 单个删除/重命名后清理批量选择中的残留条目
- Flash 目录删除返回明确的 `DIR_NOT_EMPTY` 错误
- **Flash `stat` 设置 `st_mode`**（`S_IFDIR`/`S_IFREG`），此前恒为 0，导致目录检测、删除/状态检查在内部 Flash 上失效
- **Flash 映射读取保护**：XIP 裸读窗口期保护，存储擦写期间内存映射被禁用时读 Flash 映射区不再触发 BusFault
- **XSPI 擦除忙等饿死看门狗**：4K 擦除在紧凑就绪轮询中自旋 45-200ms 不让出;实时优先级 web API 调用下把看门狗任务饿过 16s IWDG 窗口——无声复位。就绪轮询现每 64 次紧凑轮询后让出一次(内核起后 `osDelay(1)`、启动前 `HAL_Delay`;FSBL 保持裸机)
- 快速抓拍不再把刚发布的 pipe2 帧丢给开机跳帧窗口(第三个 pipe2 缓冲),并遵循 NVS `capture_storage_ai` 开关而非用卡检测覆盖

### 上传 (Upload Coordinator)

- 缺失源图的记录从 `PENDING`（永久卡住）转为 `FAILED`
- SD 删除对目录回退到 `fx_directory_delete`；静默 `FX_DIR_NOT_EMPTY` 日志（尽力清空空目录）
- 抓取：运行时 AI 结果（推理）JPEG 由 `capture_storage_ai` 门控

### 图像 / 预览

- **JPEG 缓冲区混叠**：修复抓拍和 JPEG 编码器中的缓冲区混叠问题
- **JPEG 编码尾部修正**：`jpegc` 修剪 DMA 在 EOI 后的 `0x00` 填充，并在最后一字节 `D9` 被截断时补上 EOI。修复浏览器预览底部出现马赛克、整图渲染不全的问题

### 摄像头 / 编码器 / RTMP

- **仍在写入的缓冲产生撕裂帧**：无空闲缓冲时，帧事件把 DCMIPP 重新指向它刚标记就绪的缓冲，最新帧号选择随后把一幅 DCMIPP 正在并发 DMA 写入的光栅喂给编码器。被回收缓冲现先降级为 `BUFFER_PROCESSING`，重写期间不可被选中——主管道与辅管道（推理/抓拍数据源）均已修复
- **管道停止错误路径重新武装**：`HAL_DCMIPP_CSI_PIPE_Stop` 失败时带着帧/场同步中断关闭、缓冲未复位、状态卡 `PIPE_START` 返回，帧事件从此不再运行，`camera_start` 因状态未变而短路。现返回错误前恢复中断；因 HAL stop 会清 CPTREQ，管道仍使能时重新断言抓取请求，调用方重试得以真正恢复；管道缓冲数低于两个直接拒绝
- **缓冲属主跟踪修复**：`buffer_reset` 用外层循环变量索引属主表（只有对角线条目被清，越界写过 `CAMERA_BUF_MAX_OWNERS`）；加入已占用缓冲的属主从未被记录，重复扫描比对的是陈旧条目——线程可能重复获取或被误拒；`camera_deinit` 重复释放电源句柄
- **编码器冷启动全 INTRA 锁死**：`H264EncStrmStart` 之后的状态下 `H264EncStrmEncode` 会把请求编码类型覆盖为 INTRA；初始化后首帧 HW 超时失败，此后每帧都被强制全 INTRA，重新初始化也回到同一状态——重启都无法清除。逃逸：连续 `H264ENC_OUTPUT_BUFFER_OVERFLOW` 失败步进上调率控 QP 地板（qpMin/qpHdr/qpMax 同步抬高，钳位到编码器上限；只有输出缓冲溢出才是"体积问题"——其它错误码既不推进也不复位连败计数，瞬态故障不会把已恢复的流钉死在抬高的地板上），抬高的地板在本会话内单向保持，不再回落到刚刚失败过的配置。
- **RTMP 帧尾 NAL 截断**：起始码扫描边界少查 3 字节，缓冲最后一个 NAL 没有下一个起始码——每帧推流丢失 slice 最后 3 字节（恒为编码 slice），两次转换路径一致故线上包看似完好。实测 0.35-0.46% 帧底行宏块错误；修复后 0/17197 尾字节损坏、0 解码错误行（对照同期未修复机 4027 行）

### 推流 (RTMP/RTSP)

- **RTMP 开机自动推流**：现真正读取 `rtmp_enable`——服务交由一个等待站点链路就绪后启动推流的任务（此前该标志只持久化、从不执行；姊妹 RTSP 服务早已自动启动）。等待按 30s 分片在 15 分钟预算内进行并复查运行标志，慢关联的相机仍能拿到推流（实测一次开机 10+ 分钟无 STA）；若 API 已先起流该任务让位，失败自动重试，`rtmp_service_stop` 将其退役，不会复活已停的流；任务控制块退出后回收（修复每周期泄漏一个）
- **Web 启用开关与自动启动说明**：RTMP 页新增启用开关，门控 url/密钥编辑与连接按钮（连接不再隐式启用服务；运行中关闭开关即停止推流）；RTMP/RTSP 两页均标注自动启动范围——上电开机（含长按配置模式）启动，纯抓拍唤醒不启动，默认关闭。远程唤醒来源提示现说明需内置 WiFi 已配置且在线
- **配置持久化加固**：配置 API 同时接受 `enable`/`enabled` 两种拼写（Web 曾按 RTSP 风格名 POST，开机自动启动标志在落 NVS 前被静默丢弃）；推流守卫只在推流中拒绝 url/流密钥变更，启用开关推流中仍可切换；流配置 RAM 副本保持同步，睡前配置保存不再把 RTMP/RTSP 设置回退成开机值；开机自动启动任务每次尝试前重读 `rtmp_enable`，等待期间关闭服务即被尊重；URL 拼接不再叠加路径分隔符（`rtmp://host/live//key`）

### Web 前端

- **实时预览晚连黑屏修复**：编码器每会话仅输出一次 SPS/PPS，此后连接的客户端收不到参数集，jmuxer `readyToDecode` 永不置位并静默丢帧，前端看门狗 `hardRestart` 又新建 jmuxer → 永久黑屏 + 无限加载。现按客户端维护 `sps_synced`：晚连客户端跳过增量帧，在下一个关键帧时由 hub 缓存拼出 `[SPS][PPS][IDR]` 单帧（补回 annexB 起始码）完成初始化；入流延迟至多一个 GOP（~1s）
- **连接与推流稳定性大修**:
  - **单次请求连接**：所有响应路径发送 `Connection: close` + drain，浏览器不再复用 socket——修复手机 WiFi 链路下快速切换标签页触发的 `err_network` 弹窗
  - **静态资源 etag / 304 缓存**：基于 CRC32 的 etag + `if-none-match` → 304，每次挂载的 worker/importScripts 重新拉取从 ~273KB 降到 0
  - **视频帧复制进 FIFO 再异步发送**：修复发送前缓冲被复用导致的花屏
  - **每客户端 WS 发送缓冲上限**：死连接不再无限累积内存
  - **iOS MSE 加固 + 推流诊断**：sourcebuffer 分离保护；`NET_DIAG` 标志下的网络故障查看器与 toast 标记
  - `err_network` 静默 GET 重试（1s/8s 退避），跨越 ~10s 无线电洞
- **WiFi 扫描完成后再关闭对话框**：STA 端点暴露 `scan_in_progress`，前端轮询至后台扫描真正结束——此前 reload 遮罩在首个 STA 响应即关闭并显示空/旧结果
- **已暂存 WiFi 固件不匹配期望版本时显示独立提示**：区分"已暂存但版本不同"与"尚未匹配期望值"
- 改进 FSBL 导入与烧录流程，增加重启反馈
- WiFi 重连由重试改为 **STA 轮询**机制
- 稳定 MSE 实时预览，恢复卡住的推流；改进 iOS 播放追帧，新增 media 测试；模型上传后黑预览修复
- 修复错误消息字符串显示异常
- 移动端布局修复：select 行 / RTSP URL 不再撑宽页面；HaLow "H" 徽标改为 path 渲染（替换 text）；设备工具骨架与真实布局对齐；watchdog 重启后忽略陈旧 `sourceopen`
- **数字输入失焦提交**：新增 NumberField 组件，持有键入草稿，仅在失焦或回车时解析/钳位/提交（Esc 回退）——中间值可正常键入，min-16 字段里先打 "2" 不再中途跳成 16。已迁移输入：Flash 记录上限、批量阈值、重试次数、保留时长、快速抓拍跳帧数、JPEG 质量、灯光亮度（每次提交变更只发一次网络请求，失败回弹到已持久化配置）
- **h264player 清理**：统计 interval 泄漏与离开页面遗留的孤儿播放器修复

### 视频管道

- **`video_pipeline_stop()` 死锁**：stop 无限等待各节点线程，某个 `process()` 永久阻塞的节点（抓拍/编码器/AI）会卡住 HTTP 任务并永久持有 `pipeline->mutex`。现改为 3 秒上限，超时后通过 `osThreadTerminate()` 强制终止掉队线程。

### 其它

- **补光灯 PWM 亮度**：修复亮度缩放问题
- **PIR 寄存器零值**："未配置则用默认值"守卫把 0 当作未设置哨兵，但 0 是 Web 可选的合法值（ignore_time_s 0 = 0.5s 窗口、pulse_count 0 = 1 脉冲，Web 存 value−1）——覆盖逻辑静默把这些档位改写成 4.0s / 2 脉冲，且 GET 回包与实际写入 U0 的值不一致。守卫已移除（NVS 加载路径已保证未配置设备的默认值）
- **密码学清理**：移除未使用的 si91x PSA 加密组件，整理 mbedtls PKA 移植
- `communication_type` 上报实际活跃链路，每次 cached_info 读取时刷新

## 技术改进

- APP PSRAM 启动成为唯一模式（移除 `BOOT_IN_PSRAM` 条件编译），APP 可用空间扩大至 4096K
- Flash 分区 SWAP 区域从 Flash 移至 PSRAM 区域首部
- CRC32 计算从硬件 CRC (`HAL_CRC_Calculate`) 切换至软件实现 (`CRC_Calculate`)，避免硬件 CRC 外设的字节序问题
- **XSPI NOR Flash 读取省电（~5 mA）**：`storage_power_save()` 在每次读取后将 XSPI 切回内存映射模式；新增 `storage_lock_ext/unlock_ext` 在解锁时执行同样切换。已应用到 storage、Web 资源、AI 模型、WiFi 固件等读取路径，使 Flash 在访问间隙回到低功耗状态
- OTA 上传完成后 Web 固件自动重载（无需设备重启），升级体验更流畅
- 移除旧版 si91x WiFi SDK 遗留代码
- **构建系统 — 增量编译修复**: `version_header.py` 新增 `write_if_changed()`，仅在内容实际变化时才覆写生成的头文件，保留文件时间戳不变，避免 `.d` 依赖检测误触发不必要的重编译
- **构建系统 — 移除头文件中的 `version.h` 传递依赖**: 将 `#include "version.h"` 从头文件移至实际使用版本宏的 `.c` 文件中，避免 9 个源文件在 `version.h` 变更时重复编译
- **构建系统 — 整合包目标与 CI**: 新增 `make pkg-bundle` 目标与打包校验脚本（`ota_bundle_packer.py` / `verify_ota_package.py` bundle 模式），CI 产出 bundle 产物并清理过期版本化包
- APP 版本切到 **4.3.1 发版线**（STEdgeAI 4.x generation；主版本号在 `stedgeai.mk` 中由 `STEDGEAI_BIT` 覆盖）。Web 版本 → **1.5.0.7**
- **CI 发布 app ELF 用于崩溃符号化**：构建产物发布 ELF 文件，配合 HardFault 打印做 addr2line 定位
- RTC 调度任务栈 8K → 32K，覆盖 HaLow 连接 + 上传路径的深调用帧
- 移除从未接入唤醒路径的快速抓拍协调器（`quick_bootstrap.c` / `quick_network.c`）
- **DHCP 取址提速 6-8 秒**：lwIP 2.2 将 `DHCP_DOES_ARP_CHECK` 改名为 `LWIP_DHCP_DOES_ACD_CHECK`，lwipopts.h 里的旧选项名被静默忽略，RFC 5227 ACD 探测一直开着——每次取址都因 ACK 后的探测/通告序列拖慢 `dhcp_bind()` 6-8 秒，而 DHCP 交换本身 ~130ms 即完成。现已关闭（地址来自路由器受管池，冲突漏检会在首次使用时经 ARP 自纠）：关联后链路 DOWN→UP 现在 33-125ms
- **AI pipe2 帧环加深至 3 缓冲**：DCMIPP 采集与 NN 消费之间对齐 pipe1 深度与驱动默认 `NN_BUFFER_NB=3`
- **模型批量构建脚本**（`Script/build_all_models.sh`）：编译 `Model/weights` 下全部可构建模型并逐个打包为 OTA 模型包（版本号与 `make pkg-model` 一致）；支持 `--list` / `--dry-run` / 显式选择，跳过仅配置或未注册后处理的模型，逐模型日志落在 `Model/build`
- 双语 VitePress 文档站（英文 + `/zh/`）经 GitHub Pages 部署，含生成的 Web-API 端点参考（142 端点 / 13 模块）与 PR 陈旧检查；v4.3.1 HTTP API 参考中英双发布（`Docs/NE301_v4.3.1_HTTP_API*.md`）

## 升级注意事项

1. **从 v2.1.0 升级**：Flash 分区表已重新设计——新增**独立 Web 分区**，WiFi FW / AI 分区地址移动。APP 升级后旧 Web 资源不可访问，设备进入 Web Recovery，升级**必须按序执行**（见 **[OTA 更新指南](./NE301_v4.3.1_OTA_Update_Guide_cn.md)**）：SensorExt 版 APP → Web Recovery → Web → FSBL → WiFi → 模型包 → 按需升级 HaLow 版 APP。**首步不得使用 HaLow 版 APP。**跳过或打乱顺序将导致 Web 界面不可访问。完成本版升级后，后续整机升级可使用整合包一键完成
2. **WiFi 固件需配套升级**到 `SiWG917-B.2.16.5.1.0.8`（编码 `2.16.5.108`）。设备会比对 Flash 存储版本与芯片运行版本，不匹配时 Web UI 引导升级
3. **STEdgeAI 切到 4.x generation**：APP 主版本号 = 4，模型包前缀需相应为 4.x，二者前缀不一致会导致版本校验告警
4. **FSBL 配套升级至 1.0.3.1**（双芯 NOR Flash 自适应支持，APP 编译期校验期望版本）
5. **固件包型号门禁**：OTA 包头记录设备型号，跨型号固件包（如其他机型的包）会被设备拒绝；未标注型号的旧包可正常使用
6. **从 v2.1.0 升级后首次开机将重格式化内部 Flash**（LittleFS 分区已移动）。v2.1.0 的普通抓拍不存入内部 Flash，但 **MQTT TLS CA、客户端证书和私钥文件存于 LittleFS，升级时会丢失**。已启用 MQTTS 的用户必须在**步骤一之前**保留原始证书/私钥文件，并在升级完成后重新上传。配置、WiFi 凭据等 NVS 数据与全部 SD 卡数据均保留。v2.1.0 升级者必须上传 4.x 模型包（AI 分区已移动）
